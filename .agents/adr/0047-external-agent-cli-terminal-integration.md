# 0047. External CLI Agent Terminal Integration

Date: 2026-10-19

## Status

Accepted by user direction, 2026-10-19. **Supersedes ADR `0036`, ADR `0038`, ADR `0039`,
ADR `0040`, ADR `0042` and ADR `0043`**: the built-in Agent and F# workflow system is removed,
and Patchouli integrates external CLI agents instead. The retained parts of ADR `0036` and the
unaffected revision, evidence and item-lifecycle decisions are stated under
"Relationship to earlier ADRs" below.

## Context

Patchouli had built an in-process Agent platform: a pure F# Event/Effect core
(`Patchouli.Agent`), F# workflows (`Patchouli.Workflows`), chat sessions, a workflow editor and
menu, an FSI REPL, provider transports, compaction and snapshot-synced session/workflow data.
It worked, but it made Patchouli responsible for a model runtime, a workflow language, a
conversation UI and a second MCP client, while mature terminal agents — OpenCode, Claude Code,
Codex, Gemini CLI and others — already provide better models, tools, permission prompts,
updates and their own authentication. Maintaining both paths duplicated the collaboration
surface and kept the built-in path privileged and expensive to audit.

The product direction is therefore to be the **library and MCP provider** and a good terminal
host, not an Agent vendor. That requires solving four practical problems:

1. **Discovery.** A desktop app does not inherit the login shell's `PATH` on macOS and Linux,
   and Windows installations mix native executables with `.cmd` shims. Telling a user "install
   it and restart" is not acceptable.
2. **Isolation of product state.** An agent needs a working directory, but it must not receive
   a user's source-folder paths, a Library database path or Patchouli-managed caches as its
   default workspace.
3. **A bounded collaboration credential.** An external agent can use Patchouli's MCP server,
   but only through a connection the user can inspect and revoke, and only with the existing
   MCP capability and data boundaries. Patchouli must not edit a user-global agent config.
4. **The human workflow around the terminal.** The most common tasks are not generic chat:
   they are "clean up these records", "investigate this topic", "outline this book" and
   "quiz me on this book". The product should make those tasks easy to start and easy to point
   at specific Items without pretending to drive the agent.

## Decision

### Remove the built-in Agent and workflow system

The following are deleted from the product, not hidden behind a flag:

- the F# agent core and workflow projects (`src/Patchouli.Agent`, `Patchouli.Workflows`);
- Host agent/session/workflow services (`Host/Agent`, `Host/Workflows`) and the shared agent
  driver, session inbox, FSI worker and workflow checkpoint machinery;
- the chat page, workflow editor, workflow menu entries and workflow settings;
- the `runs/agent/` and `workflows/` MCP resource trees and the old `send` instruction DTOs
  (`instruction`, `workflow`, `session`, `message_id`, `text`, `parameters` and the CLI
  `start/message/cancel/resume` forms);
- agent-session and workflow-definition payloads from snapshots.

Old snapshot import tolerates those payloads and ignores them rather than failing the
Library. MCP parameter validation is now plain C# validation of the shared Action schemas;
there is no F#/SDK bridge left on the MCP path. The built-in "full-text translation" workflow
is replaced by the Agent-independent direct pipeline of ADR `0046`.

### A compiled Agent catalog

`src/Patchouli.Core/Agents/AgentCatalog.g.cs` is generated by
`scripts/update-agent-catalog.ps1` from the Agent Client Protocol registry plus a curated TUI
adapter table. The catalog is compiled into the application so start-up performs no network or
JSON expansion; `-Check` lets CI detect generator drift.

The catalog contains nine terminal agents in display order: **OpenCode** (default), **Claude
Code**, **Codex**, **Kimi Code**, **Google Antigravity** (`agy`), **Gemini CLI**, **GitHub
Copilot CLI** (`copilot`), **Qwen Code** and **Cline**. Each entry carries a stable id,
display name, command name, interactive TUI launch arguments, per-OS absolute candidate paths,
version arguments and optional minimum version.

The ACP registry is used for its **directory layer only** — names, ids, descriptions and
distribution metadata. Its `acp` launch arguments and stdio server forms are deliberately
discarded: this integration hosts an interactive TUI in a PTY, not an ACP client. An ACP-only
entry cannot be launched in the terminal and is rejected with a stable error code.

### Layered detection with a bounded probe

Detection tries layers in order and the first executable that passes a version probe wins:

1. the user's per-agent custom path from settings;
2. the process `PATH` (`where.exe` on Windows, `which -a` on Unix);
3. login-shell resolution on macOS/Linux (`zsh`, `bash` or `sh` with `-lc 'command -v …'`),
   which recovers tools installed by a shell profile that the desktop app never sourced;
4. the catalog's absolute per-OS candidate paths;
5. a registry-derived install offer, which is information only and never downloads anything
   by itself.

Resolution has a short timeout, and one version probe is capped at **five seconds** so a hung
TUI cannot freeze the settings page. Results are cached for the process lifetime behind a
cache key that includes the custom path; "refresh" invalidates them. A launch never trusts a
cached result: it re-runs detection and probes the candidate again immediately before starting
the process. Launch failures use stable codes (disabled, unknown agent, not installed, invalid
executable, workspace failure, unsupported ACP-only entry) so the UI can offer the right next
step.

### One-click install for OpenCode

OpenCode is the default and the first agent with a managed install path. The installer
downloads the official distribution URL into a sibling staging directory, extracts the archive,
finds the executable, and promotes the extracted tree to the managed per-agent directory with
an atomic swap that restores the previous installation if the final move fails. A failed or
cancelled installation removes staging state. The installer never edits settings; the caller
persists the resulting executable path.

This first version intentionally does **not** verify a SHA-256 digest: it relies on the
official HTTPS URL and the registry metadata. That is a deliberate simplicity trade-off, not a
claim of supply-chain verification; a future hardening change can pin hashes without changing
the install/rollback flow.

OpenCode managed installation pins official `@opencode/cli` V2 native npm archives independently
of the ACP registry (which still advertises V1). x64 uses baseline binaries for CPU compatibility.
Detection continues to accept user-installed V1 and V2 through `opencode`. The catalog generator
preserves entries enclosed in `// <catalog-preserve id="opencode">` and
`// </catalog-preserve>` markers, including when refreshing registry data. Malformed or duplicate
markers stop generation. Keep the command and V1-compatible MCP config unchanged.

### Per-Library `agent-workspace/`

The workspace is `<runtime database directory>/agent-workspace/`, because Patchouli keeps one
Library per runtime database and that directory is the Library's data directory. It is created
on first launch and is owner-only (`0700`) on Unix where the platform permits it.

The workspace is the agent's current directory. It is:
- **not** a user source folder, Library database path or cache path;
- **not** snapshot content and never synced;
- safe to delete when no agent session is running (the agent's own configuration and history
  stay in its native locations).

The launch environment additionally carries explicit `PATCHOULI_AGENT_ID`,
`PATCHOULI_LIBRARY_ID`, `PATCHOULI_MCP_URL`, `PATCHOULI_MCP_TOKEN` and
`PATCHOULI_MCP_CONFIG` values only when the corresponding context is available. On Windows,
`.cmd`/`.bat` npm shims are started through `cmd.exe` because the PTY cannot execute them
directly.

### Embedded terminal

The Agent workspace page hosts a real PTY through `Porta.Pty` and renders it with
`Iciclecreek.Avalonia.Terminal`. The terminal is the product surface; Patchouli does not
screen-scrape, proxy or reinterpret the agent's conversation. The component exposes no public
PTY resize method in the pinned version, so the control's layout is the resize authority:
initial columns/rows seed the emulator grid and the layout-driven terminal applies subsequent
size changes. A compact header selects the Agent and hosts the reference/preset actions; the terminal fills
all remaining space. Switching Agents or closing the tab asks whether there is unfinished
work and requires confirmation before terminating the process. Closing a tab always ends its
terminal session; background retention and explicit stop/restart controls are removed.

### Restricted, revocable MCP configuration

The workspace page can generate a Patchouli MCP connection document for the selected agent:
`opencode.json` for OpenCode, `.mcp.json` for Claude Code, and a generic `mcpServers` document
for other clients. The document points at the local loopback MCP endpoint and, when a token
is configured, references it through `PATCHOULI_MCP_TOKEN` rather than embedding a secret in
the file. The UI writes the document **inside the Library's agent-workspace** only after the
user confirms writing and restarting. After a successful write, Patchouli automatically stops and restarts the same terminal Agent with its existing launch spec; cancellation or a failed write leaves it running. Failed restarts are reported separately from successful writes. The dialog warns that current terminal work will be interrupted. Patchouli never edits a user-global agent configuration and never writes the
token to disk. The current host supplies this token to the launched process environment as a
per-launch placeholder (there is no formal issuance API yet); the file itself contains only the
environment reference.

The generated document states the boundary: MCP authorization is governed by Patchouli's
domain permissions, structural validation, transactions and revision checks, but it is **not
an operating-system sandbox**. Revocation is explicit and local: delete the generated file,
stop or restart the MCP listener, and relaunch the Agent so the old per-launch token is no
longer in use. The document is disposable; the workspace can be regenerated at any time.

### Preset prompts and the item reference panel

The workspace page keeps the product-level workflow that generic chat lacks:

- **Four editable preset prompts** — 整理题录 (organise records), 调查主题 (investigate a
  topic), 梳理文献 (outline the literature) and 反向提问 (Socratic questioning). Applying a
  preset pastes directly into the terminal at its current input position without submitting it;
  the user edits and sends it in the external Agent's own input surface.
- **A Zed-style searchable item reference panel** over one snapshot of `ListRowsAsync`.
  Filtering is client-side and instantaneous. Confirming an entry pastes
  `Title (规范 URI: patchouli://items/{id}.yml)` directly into the terminal. Every Item type,
  including generic documents, is eligible. The URI already contains the ID, so no separate
  ID is repeated. No local source path or submitting newline is inserted; terminal pastes
  honor bracketed-paste mode without modifying the system clipboard.

The preset and reference surfaces deliberately stop at the terminal boundary. The external
agent owns its conversation, tools and confirmations; Patchouli supplies library context and
MCP access, not a second orchestration layer.

### Settings and trust model

The **Agent 集成** settings section contains an enable switch, the default agent selection,
per-agent custom paths, detection status and the OpenCode install action. Disabling the
integration keeps detection and paths but prevents launches. Settings never store agent
credentials: each CLI keeps its own authentication.

External agents are user-installed, user-authenticated processes running with the user's OS
privileges. Patchouli is not their sandbox, does not proxy their model credentials, and does
not guarantee their behaviour. The MCP capability boundary, text-only data boundary and
no-path/secret rules continue to apply to whatever those agents do through Patchouli.

## Relationship to earlier ADRs

| Superseded ADR | What this ADR replaces | What remains in force |
|---|---|---|
| `0036` Built-in sessions and workflows | The built-in Agent platform, `.fsx` workflows, chat sessions, session/workflow persistence and sync, `runs/agent/`, `workflows/` and the old `send` instructions | The **MCP collaboration surface**: user-controlled `put`/`send` capability switches, narrow atomic whole-resource and box writes, the text-only data boundary, and `runs/` as a volatile runtime projection. `runs/` now contains only `ocr/` and `translation/`. |
| `0038` Chat FSI REPL and VFS permission matrix | The chat/FSI REPL, session-local FSI worker and its session grants | The **VFS domain × verb permission matrix**, including the rule that legacy `send`/workflow/OCR grants never promote to new Action grants. `runs:translation.cancel` and `texts:translation.start` are ordinary Action rows in that matrix. |
| `0039` Typed functional agent harness workflows | The typed F# control plan, `AgentCore.chatStep`, checkpoints, receipts and workflow replay | Nothing of the harness. Its motivation — typed, inspectable automation — is not reintroduced; direct translation uses the plain engine of ADR `0046`. |
| `0040` Cache-preserving whole-prefix compaction | Built-in chat compaction, summary persistence and prefix generations | Nothing of the compaction machinery. External CLIs own their context and caching. |
| `0042` Statically declared workflow parameters | F# `Parameter<'T>` declarations, static extraction, workflow editor forms and frozen parameter snapshots | The product principle that translation settings are declared and validated independently in the **模型与翻译** card (ADR `0046`) rather than borrowed from an agent. |
| `0043` Explicit agent contexts and loop activations | Session contexts, loop activations, context bindings and activation-scoped replay | Nothing of the built-in execution model. |

The following decisions are **not affected** by this ADR:

- ADR `0027` working/committed revision model: translation runs write through the same
  committed page revisions and never advance `library_revision` merely by reporting progress.
- ADR `0028` versioned evidence URIs: external agents still consume `?rev=&box=` evidence and
  Patchouli still validates ownership.
- ADR `0030` item lifecycle, merge and purge: removing agent sessions removes one auxiliary
  data kind; Item, document, translation and OCR payload rules are unchanged.
- ADR `0034`/`0044` translation storage and writes: the direct pipeline writes through the same
  box-derived contract; external agents remain peers.
- ADR `0010`/`0023`/`0024`: the text-only data boundary, narrow writable surface and
  one-host-per-Library MCP runtime are unchanged; only the resource tree loses `runs/agent/`
  and `workflows/`.

## Consequences

- Patchouli no longer ships a model runtime, workflow language, chat UI, FSI sandbox or
  agent-session store. The build is smaller and the MCP path is entirely C#.
- Users bring their own agent and authentication. Agent quality, model choice, updates and
  permission prompts are the agent's responsibility; Patchouli only guarantees discovery,
  workspace isolation, terminal hosting and MCP access.
- Detection can still miss an executable when a shell profile is exotic or a tool is installed
  in an unusual location. The custom-path override is the explicit escape hatch, and the
  five-second probe cap keeps failure fast rather than hanging the UI.
- The workspace is product state, not a user document folder. It is safe to delete, is never
  synced, and is not part of a snapshot.
- The generated MCP configuration is a convenience, not a security boundary. Users must still
  review MCP permissions and stop or relaunch the Agent with a fresh token to revoke access;
  deleting the file alone does not invalidate a running process's token.
- The compiled catalog drifts when upstream agents change their distribution. The generator's
  `-Check` mode makes that drift visible in CI instead of failing at launch.
- Old snapshots remain importable: removed agent/workflow payloads are ignored, not applied.
  Historical ADRs remain readable as design history.
- Full-text translation no longer needs an agent; users who want agent-assisted translation
  can still use the external agent and the same MCP write contract (ADR `0046`).
