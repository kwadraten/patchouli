# 0052. FSX entrypoint metadata and non-executing configuration reads

Date: 2026-10-23

## Status

Accepted by explicit user direction. Implementation and verification are in progress;
this decision is not a claim that the migration or online-provider acceptance has completed.

Partially superseded by ADR 0053 on 2026-10-23: the configuration/capability declaration and
schema-discovery implementation is replaced by attributed Settings records. The `main.fsx`
entrypoint `///` XML metadata contract remains required.

This changes package declaration and configuration discovery under ADRs 0049/0051, not
the task-level translation execution boundary or document commit ownership.

## Context

An FSX package currently duplicates identity/version/kind in `extension.yml` and a
script-authored `ExtensionDescriptor`. Compiler and runtime parse those values separately.
The generic settings editor activates a package before opening and then checks its source
again to discover configuration fields. Metadata and translation share this editor, so both
inherit the unnecessary compilation and worker-startup cost. Closing a metadata dialog also
refreshes the translation fleet through full initialization.

The user requires all FSX extension metadata to move into `///` XML documentation on the
entrypoint and requires metadata/translation configuration windows to use one fast path.

## Decision

### One authored declaration

Every package has a fixed `main.fsx` entrypoint. Its exported top-level `extension` binding
has one XML documentation declaration containing id, kind, package version, Host API,
display name and summary. Helper scripts may still be loaded, but do not declare packages.
Translation, metadata, OCR and retrieval use the same format and parser. Retrieval remains an
existing explicit SDK capability: retaining its package kind does not deliver or select a
default vector or hybrid search pipeline.

`extension.yml` is not generated or accepted as an alternative metadata authority for new
packages. `entry: main.fsx` disappears because it adds no information. Identity and display
fields are not hand-written again in an executable descriptor: the Host materializes their
runtime projection from the parsed entrypoint declaration.

Configuration fields and capability requests retain their typed static SDK declarations.
They are not copied into XML or a second author-maintained schema sidecar.

### Reading is not executing

A bounded source-aware parser locates the declaration attached to the actual top-level
export, rather than searching arbitrary text for an XML-looking substring. XML parsing
disables external entities and DTD resolution, limits resource use and reports locations in
the original `main.fsx`. Missing, duplicated, malformed or unsupported metadata is an error;
there is no implicit fallback to translation kind.

This lightweight read performs no FCS typecheck, FSI evaluation or worker launch. Actual
activation still checks code and declared capabilities, verifies the implementation kind
against package metadata, and obtains user authorization independently. Readable metadata
is never proof that code is checked or authorized.

### One configuration-description path

The Host exposes immutable descriptions to all settings clients. An existing checked Active
generation supplies its description without being rechecked. Bundled packages also have a
build-derived description index generated by the real static checker and embedded into
the application. Its package snapshots and fingerprints must match the runtime factories,
including engine-specific default substitutions and loaded helper sources.

The index is derived build data, not another package-author file. It cannot authorize code
or suppress execution-time validation. Cache identity includes complete source fingerprint,
Host API and relevant checker/reference identity. Unknown or stale third-party source can
open in an explicitly unchecked/source-only state; a form is not fabricated by executing it.

The same generic dialog serves metadata and translation. It becomes visible before loading,
can cancel loading on close or selection/library change, and never initializes unrelated
workers merely to list packages or refresh after closing. Explicit source check/save/apply
and sample execution retain their separate operations and failure semantics.

### Compatibility and immutable history

The package-format/Host API compatibility boundary must be explicit in implementation.
Old YAML packages receive an actionable migration failure rather than being silently
interpreted through a second parser. If a converter is provided, conversion is an explicit
source operation producing a new fingerprint and checked generation.

Active and LKG snapshots are not rewritten in place. Existing leases keep their frozen
generation until drained; source drafts, saved configuration, grants and committed document
data retain their ownership. Copying a package edits only the structured entrypoint id,
not unrelated occurrences of the old id inside source text.

## Consequences and verification

- Ordinary configuration opens require zero extra static checks and zero new workers,
  including cold discovery of bundled packages through the generated index.
- All built-in scripts, fake packages, worker tests, editor-copy tests and author examples
  migrate together. A source hash or compiler/API mismatch invalidates descriptions.
- Source spoofing, hostile XML, duplicate declarations, implementation-kind mismatch,
  immutable snapshot migration and cancellation are regression boundaries.
- Build generation and parser validation are tested independently from live translation
  endpoints. Protocol fixtures passing do not establish Google, Microsoft or Tencent
  availability on a user's network.

Actual commands, pass/fail counts and remaining gaps belong in
[extension validation](../protocols/extension-validation.md).
